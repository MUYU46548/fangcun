>

>

> 1. **看不懂** —— 通篇 gate / status token / steering docs / SHALL / spec delta，**没有一个词是从用户嘴里长出来的**，

## 一、结论先行

**这个品类已经饱和，而且不是"一堆工具"，是一整套成型的方法论：SDD（Spec-Driven Development）。**
它已经沉淀出稳定骨架，各家只是取舍不同。方寸现在**一个机制都没有** —— 它有的是「任务状态」，不是「产物状态」。

**五个必抄（按投入产出排序）**

| # | 机制 | 一句话 | 出处 |
|---|---|---|---|
| 1 | **状态 token 是唯一 gate** | 文件存在 ≠ 批准。`design.md` 躺在目录里不是绿灯，只有 `.status` 里那个 token 才算 | pi-sdd-kit |
| 2 | **steering docs 作持久项目记忆** | 产品/技术栈/约定/原则/边界，每次会话重载。**"技术的理由"比技术本身值钱**（"我们用 PostgreSQL 是因为支付记录要 ACID" 这一句能防三个月后模型又建议换 SQLite） | pi-sdd-kit |
| 3 | **只读 analyze** | 交叉检查「有需求没任务」「有任务没需求」「违背原则」，**只报不改**。原则冲突永远是 CRITICAL | spec-kit |
| 4 | **证据门** | 任务不能自报完成。每个适用 gate 都要证据（code/tests/integration/deploy），且证据要被**产物**验证，不是被作者验证 | Squelette / Operational Memory Gates |
| 5 | **规模自适应流程重量** | Level 0 单点改动用 quick-spec 一条路，Level 3 才用全流程。**这是反死板的正解** | BMAD Level 0–4 / spec-kit 双路径 |

**三个绝对不抄**

| 不抄 | 为什么 |
|---|---|
| **分数门**（某实现的 PRD ≥ 90/100 才算过） | 伪精确。同一个模型两次打分不可复现，人无法审计"为什么是 87 不是 91"。它把不可判的东西包装成可判的 |
| **一套流程套所有事** | 五阶段流程套到"改个按钮"上，人就开始应付流程 —— 这就是暮雨说的"更死板、害处更大" |
| **无限评审循环** | YYLO 明确用 `REVIEW_FINDINGS_EXHAUSTED` 终止，而不是"审到没问题"。没有终止条件的评审会变成永久阻塞 |

**方寸的真正位置（这是全文最重要的判断）**

所有 SDD 工具都有两个共同限制：**① 只在单个仓库里；② 寄生在 coding agent 里（CLI + markdown，挂在 Claude Code / Cursor / Pi / Hermes 上）**。

没有一个能做到：
- 跨项目看「六在途项目各自走到哪一步、哪个 gate 没过」
- 把**人的决策**当一等公民跨项目管（Squelette 有 `HD-002` 编号，但只在一个仓库）
- 让**人**（而不是 agent）一眼看到全局

而方寸的验收线本来就写着「**六在途项目在哪一步 / 下一步 / 卡在谁，一屏可见**」。

→ **方寸该做的是「跨项目的 SDD 状态层 + 人的决策台」**：读它们的产物，把 gate 状态 / 未拍板决策 / 证据缺口汇总到一屏。
→ **不该做的是再写一个 SDD 引擎**（spec-kit 91k stars、BMAD 48k、OpenSpec 52k，都比方寸做得好，而且免费开源）。

## 二、逐家细节

### 1. pi-sdd-kit —— 最接近方寸的一家，重点研究

单人/小团队、文件式、无重工具、明说「no heavyweight tooling」。

**流程**：`IDEA → PLAN → PRD → SPEC → TASKS → EXEC → REVIEW`，每阶段一个人工 gate。

**目录结构（关键）**

```
.ai/
  steering/                 ← 持久项目记忆，每次会话重载
    product.md                是什么、给谁、明确不是什么
    tech-stack.md             栈 + **每个选择的理由**
    conventions.md            路由/错误/鉴权怎么组织
    principles.md             不可协商项（"所有金额计算用整数，绝不用浮点"）
    lp.md
  strategy/handoff/         ← 可选上游（从别的包接进来）
  sdd/
    INDEX.md                ← 看板，**不是编号来源**
    PLAN.md
    handoff/sdd-brief.md    ← 下游交付契约
    ideas/001-feature-idea.md
    specs/001-feature-name/
      .status               ← **唯一的 gate**
      requirements.md
      design.md
      tasks.md
      review.md
      decisions.md
```

**`.status` 的全部取值**（这就是它的状态机）

```
idea:exploring / idea:captured
plan:draft / plan:approved
requirements:draft / requirements:approved
design:draft / design:approved
tasks:draft / tasks:approved
implementation:in-progress / implementation:done
review:done
```

三条硬规矩（原文语义）：
1. **草稿可以存，但草稿不解锁任何 gate**
2. **产物存在永远不等于批准** —— "a design.md sitting on disk is not a green light"
3. 实现期间**不许悄悄改需求或设计**

还有一句值得抄进方寸注释的：
> **"Gates that live in your head are culture; gates that live in a file are enforcement."**
> （活在脑子里的门禁是文化，活在文件里的门禁才是强制。）

**其他可取之处**
- **澄清内嵌，不加阶段**：需求澄清在 PRD 步骤里做成「2–4 个具体选项 + 各自影响」，就绪检查放在 TASKS 里 —— 少命令、同样严格
- **编号从实际目录取下一个**，`INDEX.md` 只是看板，不是真源（防止编号靠一个会写坏的索引文件）
- **语言策略**：产物用用户的对话语言写，但**路径、状态值、ID 永远英文**（"标识符不是散文"）
- `sdd-status` 是**只读**看板，输出：已有的 idea / 当前 plan / 各 spec 状态 / blockers / **next safe action**

### 2. GitHub spec-kit（91k stars）—— 命令链做得最干净

```
/constitution   写 .specify/memory/constitution.md
                每条原则**必须可测**（"代码要干净"不合格）
                带语义版本 + 批准日期 + Sync Impact Report
/specify        写 specs/001-name/spec.md
                用户故事带 P1/P2/P3，Given/When/Then 验收场景
                FR-NNN 编号；**[NEEDS CLARIFICATION: …] 最多三个**，超了就问你
                规格里不许出现类名/表名/库名
/clarify        结构化提问，答案写回 spec.md
/plan           读 spec.md 写 plan.md（**单向，永不回改 spec**）
                再产出 research.md / data-model.md / contracts/ / quickstart.md
                **plan.md 内含 Constitution Check gate**，research 前后各评估一次
                违反必须 justifies 在 Complexity Tracking 表
/checklist      **"a unit test for the spec, not for the code"**
                例：「每个入口都写了授权规则吗」
/tasks          tasks.md 按阶段（setup / foundational / 每个故事一阶段 / polish）
                任务带 ID + [P] 并行标记 + [US1] 故事标签
/analyze        **严格只读**：报「有需求没任务」「有任务没需求」「违背原则」
                原则冲突永远 CRITICAL
/implement      逐阶段执行，标记 [X]
                **只允许读 checklist 的勾选状态当 gate，不许改勾选** —— 勾选权归人
/converge       读三份 + 代码库，把发现 append 到 tasks.md
```

**最值得抄的一条**：`/analyze` **只读**、且**允许它说"这里没有任务覆盖"而不许它补**。
它把"发现问题"和"修改内容"分开，人保留修改权。

**次值得抄**：`/implement` 不许改勾选 —— 这是"AI 不能给自己发绿卡"的实现级保证。

### 3. BMAD-METHOD（48k stars）—— 角色最多，且有反死板设计

**十个角色**：Mary 分析师 / John 产品 / Sally UX / Winston 架构 / Bob SM / Amelia 开发 / Murat 测试架构 / Quinn QA / Paige 技术写作 / Barry 单人快流。

**四阶段**：Analysis（可选）→ Planning（PRD）→ Solutioning（架构 / epics-stories / implementation-readiness）→ Implementation（sprint-planning / create-story / dev-story / code-review / correct-course）。

**最值得抄的是 Project Levels（反死板的核心）**

| Level | 规模 | 推荐流程 |
|---|---|---|
| 0 | 单点改动 | `quick-spec → quick-dev` 两步 |
| 1 | 小功能（1–10 故事） | brief → tech-spec → dev |
| 2 | 中等（5–15 故事） | brief → PRD → arch → sprints |
| 3 | 复杂（12–40 故事） | 全流程 |
| 4 | 企业级（40+） | 全流程 + 测试架构 |

**流程重量按规模自适应**，不是一律全跑。这一条直接解决"死板"问题 —— 而方寸现在连这个概念都没有。

**另一个可抄：Party Mode** —— 多个 agent 在同一会话里讨论，各自保持人格，可赞同/反驳/补充。这是「评审团队」的最低成本实现（不需要真起五个进程）。

**不抄**：某实现里用「PRD ≥ 90/100 分」「Design ≥ 90/100 分」当质量门。分数由模型自己给，不可复现、不可审计。

### 4. Specflo —— 产物外置最彻底的一家

四阶段：`brainstorm → spec → plan → execute`。

**核心设计一句话**：
> **every artifact persisted as plain Markdown files on disk rather than held in a model's context window**

它的目标用户是**小参数本地模型**（上下文装不下），所以把相位状态、校验门、任务追踪全部外置到 markdown。
→ 这一点直接印证方寸的底层赌注（md 为真源）是对的。

**可抄的具体机制**
- **稳定 ID**：`D-NN` 决策 / `REQ-NN` 需求 / `T-NN` 任务
- **双向需求-任务覆盖校验**（req→task 和 task→req 都查）
- **无环依赖检查**（acyclic dependency checks）
- **validate-then-move 相位迁移**：先校验再改状态，不许先改后补
- **需求可被取代（supersession）**：校验时沿取代链追到最终有效的那条 —— 这比"删掉旧需求"好得多，历史留得住

### 5. OpenSpec（52k stars）—— 改动管理最严谨

三态状态机：`proposal → apply → archive`。
`openspec/` 下分 `specs/`（当前状态，真源）与 `changes/`（进行中的提案，含 proposal.md / tasks.md / delta specs）。

**可抄**：
- **delta 标记**：提案必须说清哪些流程 MODIFIED、哪些 ADDED —— 老项目改造时的最小信息
- **`validate --strict`**：缺 GIVEN/WHEN/THEN 场景**直接拒**，不是警告

### 6. Squelette —— 治理做得最硬

标准库 Python 控制器（`scripts/project_control.py`，无服务），**"fails closed rather than advising"**（不合规就拒，不是建议）。

**可抄的四件**

1. **Work Item 声明授权路径**：preflight 拒绝路径外的写。demo 里 agent 顺手改了 `modules/billing/invoice.py`（没人要求），preflight 直接 `exit 1` + `BUSINESS_CHANGE_AUTHORIZATION` + `AUTHORIZED_PATHS` 两个失败项
2. **Proof of reading**：`context-manifest` 列出所有治理文档的 SHA-256 + 全局 digest；`start` 不带 digest 就拒。
   它自己说得很克制：**"What this proves is narrow and exact"** —— 只证明"工作是从当前文本开始的"，
   **不能证明"读懂了"**。这种自我限定值得学。
3. **证据门**：每个适用 gate 都要证据（code / tests / integration / deployment / runtime-proof），
   创建 Work Item 时就要写 `--close-condition`（"测试通过且分支合入 main"）
4. **一条 Work Item 一条分支**，commit hook 装在 worktree 外，**不许 `git add -A`**

另有一条产品细节值得方寸照做：**报告用 owner 选的语言（EN/FR），但 check 名、状态值、失败消息保持英文** —— 标识符不能翻译，翻译就不可对账。

### 7. Operational Memory Gates —— 21 条机械门的范本

MIT 规范 + 参考实现。**21 条 pre-code gate，每条都被标注为「生产事故机械化」或「纪律机械化」**。

最关键的一个比例：**20 条拒绝（非零退出），1 条建议**。
→ 门禁的信噪比是有配比的：绝大多数必须硬拒，只留极少数当提醒。全都"建议"等于没有门。

参考脚本**故意写死作者的技术栈** —— 它的定位是"可检查的规范"，不是开箱工具。这个自我定位也很值得学：**规范比工具更容易被抄对**。

### 8. 治理向的另外四家（挑着看）

| 项目 | 一个可抄的点 |
|---|---|
| **MREA** | 三角色分离（Architect / Auditor / Implementer），**明确防"self-validation bias"**（自己验自己） |
| **Okto Pulse** | spec 驱动 SDLC 工作台，**在权限层**强制独立验证与证据门；带知识图谱捕捉「偏离记录决策」 |
| **Okto Nexus** | **single-winner task claims**（多 agent 抢同一任务只有一个赢）+ 崩溃可恢复的 handoff 历史 |
| **YYLO** | merge queue 按风险分级审（低风险无语义审、高风险两个顺序审），**以 `REVIEW_FINDINGS_EXHAUSTED` 终止** |
| **sofagent** | 24 条 commit-time 审计（secrets / 越界编辑 / 盲改 / prompt injection）+ HMAC 签名审计史 |
| **Aide** | **本地 dashboard 跨项目排队 spec**，headless 跑 create/analyze/implement/archive，**只在合并结果测试通过后合并** |

**Aide 是唯一在"跨项目"上和方寸撞车的**。差别：它管的是 spec 队列（多仓库排队跑），方寸管的是**项目组合状态 + 人的决策**。

## 四、方寸的追赶路线（分三期，每期都能单独用）

### 一期：变成合格的 SDD 宿主（不写引擎，只读产物）

1. **支持 `.status` gate 的读取与显示**
   方寸的卡可以挂到 `specs/001-name/`；看板显示该 spec 的 `.status` token。
   **卡的「完成」不再只看人点，而是看 gate**：`tasks:approved` 之前不许进「进行中」。
2. **编号从目录取，不建索引真源**（照 pi-sdd-kit 的反面教训：`INDEX.md` 只是看板）
3. **跨项目一屏**：六个项目 × 各自最新 spec 状态 × blockers × next safe action
   —— 这一屏就是契约验收线里那句「六在途项目在哪一步一屏可见」，只是数据源从"卡的状态"换成"**产物的 gate**"

> 一期不改任何人的仓库，纯读。方寸从"中转站"变成"**gate 的显示器**"。

### 二期：只读 analyze + 与决策板对撞

1. **机械可判的检查**（全部不需要 LLM，全部"只报不改"）：
   - 有需求没任务 / 有任务没需求（双向覆盖）
   - 任务依赖成环
   - 需求没有可验收条件（缺 Given/When/Then）
   - 规格里出现类名/表名/库名（spec 越界到 how）
   - `[NEEDS CLARIFICATION]` 超过 3 个
2. **方寸独有的一条**：**与 `decisions.md` 的有效决策对撞** —— 需求违背已拍板的事，直接点名。
   这是所有 SDD 工具做不到的，因为**它们看不到你的决策板**。
3. **输出形态**：报告 + 精确到行，**不修、不补、不打分**

### 三期：steering docs 常驻

把方寸现有的 `policies/` + 决策板 + 契约，整理成 `steering` 形状（product / tech-stack / conventions / principles），
**通过 MCP 在每次会话开头自动注入**，而不是等人手动拼 contextPack。

价值不在于"多一个文件"，在于 **tech-stack.md 里那句理由**：
> "我们用 PostgreSQL 是因为支付记录要 ACID" —— 这一句能防三个月后模型又建议换 SQLite。

方寸的 `decisions.md` 已经有这个内容，只差"按 steering 形状组织 + 自动重载"。

## 五、抄的时候必须守住的三条

1. **规模自适应不是可选项**。方寸任何新流程都必须先回答：「改个按钮要用几步？」
   答不上来的设计，就是暮雨说的"死板、害处更大"。
2. **只读的必须是只读**。`analyze` 型能力一旦被允许"顺手改一下"，人就不再信任它的报告。
3. **不许自己发绿卡**。所有 gate 的通过标记必须由人（或由产物验证）产生，AI 只能读不能写。
   spec-kit 那句「允许读勾选、不许改勾选」是这条原则的实现级表达。

## 六、本机实证：方寸自己就是 OpenSpec 用户，而它不知道

调研过程中扫本机，发现一件自相矛盾的事：

```
fangcun/openspec/
  config.yaml                                  schema: spec-driven，Language: zh-CN，SHALL/MUST 保持英文
  specs/.gitkeep                               ← **空的**
  changes/archive/.gitkeep                     ← **空的（从未 archive 过任何 change）**
  changes/fix-data-dir-detection/
    .openspec.yaml                             created: 2026-09-21
    proposal.md                                Why / What Changes / Capabilities(New+Modified)
    design.md                                  Context / Goals-NonGoals / Decisions
    specs/data-dir-resolution/spec.md          Purpose / ADDED Requirements / Scenario(WHEN-AND-THEN)
    tasks.md                                   5 个任务，**全部 `- [ ]`，0 个勾选**
```

**而这个改动早就做完了**：`desktop/src/main/data/index.ts:77` 就是那段
`for (let i = 0; i < 5; i++)` 的父目录上溯逻辑，和 spec 里写的场景逐条对得上。

**三件事同时成立**：
1. 方寸 2026-09-21 真的按 OpenSpec 走了一轮（提案 → 设计 → 规格 → 任务），产物完整、质量不差；
2. 代码按规格写完了，**但 5 个任务一个没勾、从未归档**；
3. 方寸的界面**完全看不见 `openspec/` 目录** —— 它自己的规格状态对它自己不可见。

**这条实证比任何调研都重要**，因为它同时证明三件事：
- SDD 产物是**有用的**（当时那轮确实按规格走，`initPaths()` 到现在还在用）
- **gate 不落地就等于没有流程**（做完的事，状态显示"未开始"）
- 方寸缺的正是「读产物 + 显示 gate」这一层 —— 而这层**不需要任何 AI**

**一期第一个验收用例（现成、可立刻验）**：
一期做完后，方寸那一屏上应该立刻出现
> `fix-data-dir-detection · 5 个任务未勾选 · 但代码已实现 · 该勾选并归档了`

这就是「方寸发现自己」的第一个动作。用真数据验，不用造夹具。
