# 方寸为什么「12 格全绿，东西不存在」

- 日期：2026-11-15
- 触发：暮雨「0.6.43 又怎么样？0.6.9999999 都没用。我要的东西根本不存在，根本没做出来」
- 本文件由 agent 手写（不是脚本生成），每条判断都带出处；推断的地方标「推断」。

---

## 0. 一句话

**P0–P11 十二格判的是「代码里有没有这句话」，不是「他有没有真用上」。**
所以 12/12 绿与「东西不存在」可以同时为真 —— 它们本来就不是同一件事。

---

## 1. 判据口径的证据（可复算）

`task-data/plans/fangcun-base.md` 46 条判据：

| 类型 | 条数 | 它其实证明了什么 |
|---|---|---|
| `str:` | 28 | **源文件里含某句话**（多数是注释） |
| `file:` | 6 | **某个文件存在** |
| `cmd:` | 12 | 某个测试套件退出 0 |
| `num:` | 0 | —— |

实测：28 条 `str` 判据里 **6 条要匹配的文字只出现在注释行里**
（`grep` 命中行全部以 `*` / `//` / `#` 开头）。也就是说那 6 格验的是「我写下过这句话」。

计划卡自己也承认这个分层（原文）：

> `str:` / `num:` / `file:` = **可复算事实** …… 但它**证明不了行为**，只防"能力被悄悄摘掉"。

**问题不是这个分层错了，是 46 条里 34 条（74%）落在"证明不了行为"那一层，
而"完成"这个词是由它们判出来的。**

---

## 2. 契约 ② 验收线要求的，与计划卡跑的不是一回事

契约 ② 原文的验收线 = 两条同时成立：

1. 六在途项目「在哪一步 / 下一步 / 卡在谁」**一屏可见**；
2. **契约机制本身在方寸可用**。

而 P0–P11 十二格里，**没有一格的名字里出现「一屏」或「契约」**。
一屏（trip board）是 0.5.0 就做掉的，契约索引在 Q1 —— 两者都**不在当前这版作战计划的跑道上**。

⚠ 契约 ③ 那段「当前断点」写着「契约文件 0/13」「一屏视图不存在」，**那是 2026-10-05 的快照**，
到今天已过期 41 天，但仍挂在契约正文里当"现状"。实测今天：

```
立项契约.md 覆盖：12 / 14
缺：songtao-zhenyun（已封存）· dsh-fangcun
```

**契约本身在说假话，而没有人回头改过它。** 这与「界面在说谎」是同一类病（见长 Loop §3）。

## 4. 产品定义的突破点，被实现成了它明确说"不算"的东西

`docs/产品定义-方寸-20261027.md` 把突破点压成一句话：

> **过去 N 天，这个项目花了多少 token，产出了几件"真的被用起来"的东西？**
> "真的被用起来" = 验收通过 / 被合并 / 已发布 / 被别处引用。
> **不算"卡变完成"——那是自报**（004 卡的证据门）。

而 `desktop/src/shared/waste.ts` 的"产出了什么"这一格，实现的是：

```ts
// ② 产出了什么 —— git 提交 + 完成的卡（两边各算各的，都不猜）
if (done !== null) parts.push(`${done} 张卡完成`)
```

**自检报告 2026-11-15 实际输出**：

```
产出了什么（近 30 天）：356 次提交 · 198 张卡完成
```

产品定义说「卡变完成不算」，实现把它当成了产出 —— **口径与产品定义直接相反，
而且它每天被印在自检报告上。** 这不是"没做"，是"做成了反向的"。

## 5. 「被否掉的提案」：产品定义标了 ❌，对象至今不存在

产品定义那张表里，四种数据只有一格标着 ❌ 完全没有：

| 数据 | 方寸 | 外部 agent |
|---|---|---|
| 被否掉的提案 + 否掉的理由 | ❌ **完全没有这个对象** | ❌ 一次会话结束就没了 |

实测：`desktop/src/main/services/ideas.ts` 有「已否决」状态，但那是**想法（idea）**，
不是"某个提案被否了、理由是什么"。三张 `p0-1-收口` 卡（十件 bug / 打包发版 26 条 /
检索日志 25 条 / 测试接入 33 条 / 界面视觉 16 条 / 规划决策 17 条）正是他**一天里否掉的一大堆东西** ——
而它们躺在待办里，没有任何结构记录"这是被否的、理由是什么、所以省下了多少"。

他自己把这件事的价值说得很清楚：

> 「**今天方寸救不了自己，靠外部 agent 也救不了自己，关键在于找到那个突破点，
> 让 token 不在错误的路线上继续白费**（比如我今天否掉的一大堆东西，实则节约了大量成本）。」

## 8. 这一轮我打算怎么避免第 N 次白干

1. **判据先于实现，且必须是行为判据**：先写会红的断言，再写实现。
2. **每格必须有一个"人会用到它"的验收动作**，不是文件里有一句话。
3. **不许再用 `str:` 判"能力存在"** —— 上一版 74% 是这一类。
4. 做完的量法：**由他打开一次并说"这就是我要的"**，不是自检报告绿。

> 推断（明确标注）：我认为 §7 第 1、3 条是真正能产生"他原来不知道的事"的位置，
> 第 2、5 条是把他从"每次都从零讲一遍"里解放出来的位置，第 4 条取决于他改不改 D-077。
> 这是我的判断，不是已经验证的事实。
