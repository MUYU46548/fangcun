## 二、逐条

### P0-1 Hermes 会话内 MCP 工具表陈旧

**现象**：本会话可调 32 个方寸工具；真实桥握手返回 37 个，缺的正是这批新的 5 个：`decision_list` / `project_charter` / `stage_plan_get` / `smap_propose` / `smap_apply`。第 7、8、10 条测试因此只能走桥的原始 JSON-RPC，不是会话原生工具。

**证据**：

- `node scripts/check-agent-mcp.cjs --readonly` → `✅ Hermes 握手通过（37 个工具）`
- 本会话 `tool_describe` 对 `mcp__fangcun__smap_propose` 返回 `not_found`
- 缓存文件 `C:\Users\muyu\AppData\Local\hermes\cache\mcp_schema_cache.json` 的 `fangcun` 条目：`tools.length = 32`、`written_at ≈ 09:17`、`ttl_ms = 0`、`fingerprint = 16a603809034917e`

**根因**：

1. 会话启动时把 MCP 工具表打进快照，会话内不刷新 —— 这一层方寸管不到。
2. Hermes 侧的 schema 缓存指纹只 hash 连接配置，不含服务端工具集：`hermes-agent/tools/mcp_schema_cache.py:44` 的 `config_fingerprint()` 只取 `command / args / url / transport / tools.include|exclude`。方寸装新版本后命令没变 → 指纹不变 → 缓存继续命中旧清单。

**建议修法**（三选一或叠加）：

- 方寸侧：装完包 / 首次启动时，在「接入其他 Agent」区提示「已更新 MCP 工具集，请重启 agent 会话」，并把这句话写进 `skills-sync.json` 的同步结果里显示。
- Hermes 侧：`config_fingerprint` 纳入服务端版本信息（如 MCP `serverInfo.version`，方寸已随包给版本），或在 `skills` 那类入口提供一次「刷新 MCP」动作。
- 兜底：把 `ttl_ms = 0` 改成有限 TTL（现在 0 被判过期，但会话快照仍是旧的 —— 说明单靠 TTL 不够，必须解决会话快照）。

**验证口径**：装新版方寸后开新会话，`tool_describe mcp__fangcun__smap_propose` 应返回 schema；`hermes skills list` 之外再补一条工具数断言（期望 37）。

### P0-2 自检脚本对折行 YAML 误报

**现象**：`check-agent-mcp.cjs` 报「DSH 的 command 指向的文件不存在」+「DSH 握手失败」；实际该 exe 存在，且 DSH 已把它拉起来（PID 16316，父进程 `DeepSeek Harness.exe`，14:50:53 起）。

**证据**：

- `scripts/check-agent-mcp.cjs:52`：`const cmd = /command:\s*(.+)$/m.exec(seg)`，文件头注释写明「格式固定，不引 yaml 依赖」
- `~/.dsh/profiles/desktop/cordis.patch.yml` 里该行被折成 88 列：`...dist\ele` + 换行 + `ctron.exe`；args 同样在 `bridge-stan` + `dalone.js` 处折行
- 用 PyYAML 正式解析同一文件：`command` = `…\dist\electron.exe`、`args[0]` = `…\bridge-standalone.js`，两个路径 `os.path.exists` 均为 True

**根因**：自检脚本假设「一行一条路径」，遇到折行（编辑器/格式化工具的正常产物）就只取到半截路径，于是「文件不存在 → 握手必失败」连锁假红。

**建议修法**：

1. 改用 YAML 解析（Node 侧加 `yaml` 依赖，或复用方寸已有的解析代码路径）。
2. 若坚持不引依赖，至少实现折行拼接：双引号标量里「行尾无反斜杠的换行」按 YAML 规则折成空格、带 `\` 续行则直接拼接 —— 但这条路容易再翻车，优先选 1。

**验证口径**：新增回归 —— 喂一份折行版 `cordis.patch.yml`，断言解析出的 `command`/`args` 完整且 `existsSync` 为真。

### P1-1 DSH 指向 dev 构建

**现象**：DSH 的 `mcp-fangcun` 用的是仓库 dev 树：

```
command: E:\CODE\CangKu\fangcun\desktop\node_modules\electron\dist\electron.exe
args:    E:\CODE\CangKu\fangcun\desktop\dist\main\mcp\bridge-standalone.js
```

Hermes 用的是安装版 `E:\Software\fangcun-desktop\方寸.exe` + `resources\app.asar\dist\main\mcp\bridge-standalone.js`。

**证据**：`hermes config get mcp_servers.fangcun` = 安装版；运行进程 PID 10832 父进程为 Hermes 的 `python.exe`（15376）；dev 那条 PID 16316 父进程为 `DeepSeek Harness.exe`（6408）。

**影响**：DSH 侧 agent 跑的是 dev 代码，与用户在安装版里看到的行为可能不一致；`git pull` 后 dev 构建未重编时，DSH 拿到的还是旧 bundle。

**建议修法**：DSH 配置改指安装版（与 Hermes 同款三段：command / args / `ELECTRON_RUN_AS_NODE: '1'`）。方寸「接入其他 Agent」页生成 DSH 段时，应按**当前运行态**取 exe 路径（`process.execPath` 在安装版下即 `方寸.exe`，dev 下为 electron.exe —— 这正是「dev 里点接入写开发路径」的由来），并在装机后提示重接。

**验证口径**：改完重启 DSH，`check-agent-mcp.cjs` 两侧都「command 存在 + 握手通过」，且进程表里不再有 dev 树的 `electron.exe ... bridge-standalone.js`。

### P1-2 作战计划 overview 不覆盖 `_parked`

**现象**：`stage_plan_get {}` 只报 1 份计划（`fangcun-base.md`，8 格全完成、待裁决 0）。实际 `task-data/plans/_parked/` 下 11 份计划卡、每份 2 格「待裁决」= 22 格，全部不可见。

**证据**：`desktop/src/main/data/plans.ts:62-63` —— `listPlanFiles()` 过滤 `!f.startsWith('_')`；`desktop/src/main/mcp/tools.ts:948-963` 的 overview 正是基于它统计。

**影响**：第 7 条的「主动说 N 张阶段卡等你裁决」在这套数据下永远说 0，用户会以为「三查形同虚设」是模型不听话，其实是口径没覆盖。

**建议修法**（择一，需暮雨拍板哪种是「真待裁决」）：

- overview 增加 `parked: { files, stages, pending }` 汇总行（只报数不展开），agent 就能说「另有 11 份停放计划共 22 格待裁决」；
- 或明确把 `_parked` 定义为「不参与待裁决统计」，并在返回体里写一句 `parkedExcluded: 11` —— 让 agent 知道有东西被排除，而不是以为天下太平。

**验证口径**：调用 `stage_plan_get {}`，返回体里能看到 `parked` 计数（或排除说明），且与 `_parked` 下实际格数一致。

### P1-3 里程碑表与阶段卡状态不同步

**现象**：`task-data/plans/fangcun-base.md` 的「## 里程碑」表里 P1-P7 状态仍写「待裁决」，而同文件「## 阶段卡」P0-P7 全是「完成」。

**证据**：该文件 65-71 行 vs 148 行起的阶段卡小节；`stage_plan_get` 数的是阶段卡（8 完成 / 0 待裁决）。

**影响**：读「里程碑」表的人（包括 agent）会得出「7 格在等裁决」的相反结论；这正是 P1-2 那条「AI 不用三查」体感的另一个来源。

**建议修法**：两处状态由同一来源派生（阶段卡为准，表自动同步），或至少在页面/工具返回值里标注「里程碑表为规划期快照，实时状态以阶段卡为准」。

**验证口径**：改完后 `grep -c '状态: 待裁决' task-data/plans/fangcun-base.md` 与该文件阶段卡的实际待裁决数一致。

### P2-2 `plan_pending` 与 `stage_plan_get` 命名易混

**现象**：`plan_pending` 查的是「规划卡（`type: plan`）里 `plan_status` 为 draft/active 的任务」（`tools.ts:851-856`），与「作战计划阶段卡」（`task-data/plans/*.md`）是两套完全不同的数据。技能卡把它们并列为「开工三查」，但名字看不出区别。

**影响**：只调 `plan_pending` 的 agent 会以为「没有待裁决」，实际可能有一堆阶段卡（见 P1-2）。

**建议修法**：`plan_pending` 的返回体里加一行指引（「阶段卡请用 `stage_plan_get`」），或在技能卡「①.5 开工三查」把两者写成一条动作。

**验证口径**：只调 `plan_pending` 时，返回体能让人知道还有另一套数据要查。

### P2-3 老格式方针卡的落地保真未验

**现象**：`policies/memory-sanctuary.md` 与 `policies/bianjishi.md` 是早期四节格式，**没有「## 结构地图」节**。`smap_apply` 走 `savePolicy()` 整份重写（`services/policies.ts:114-149`），会把这一节补出来，但「其余四节逐字未动」在缺少该节的文件上尚未实测。

**风险**：`savePolicy` 是**整份重新拼装**（只保留可识别的四节 + `preserveSections` 兜住的未知节），若老文件里有非标准段落，可能被重排或丢失。

**建议修法**：拿一份老格式卡的副本跑一次 `smap_apply`（或在测试里构造），前后 diff 只允许「`> 更新:` 时间戳 + 新增 `## 结构地图`」两处变化。

**验证口径**：上述 diff 断言进回归（`e2e-smap-proposal.cjs` 里加一条老格式用例）。
