## 为什么是这一件（三条事实逼出来的）

1. 账上 **99.3% 的 token 是 cache_read**：现在的"花销"数字量的是上下文长度，不是劳动量。
2. **93% 的 token 归不到任何卡**（217 条里只有 4 条带 `card=`）：不修，投入产出永远是分母不清的平均数。
3. 方寸自己的调用只占 **0.0024%**、失败率 **50%**（plan-draft 3 挂 2、archGenerate 2 挂 2，全死在"不是 JSON"）：
   它的价值不在省钱，在**别再白跑**。

> 判据一句话（照 P5 的口径要求）：**0.7.0 交付后，能回答"过去 N 天花了多少新 token、产出几件真被用起来的"，

## 顺序与依赖

```
W3（结构化修复，半天）─┬─→ W5 架构图第一刀（根因同一条：不是 JSON）
                       └─→ W1 口径 ──→ W2 归因闸 ──→ 自检报告（引用 W1/W2 数字）
W6 冻结手搓（半天，随时可开，但要在 W5 之前）
W4 竞品 P1（数据层 + CLI，1 天，与 W1/W2 并行）
```

**为什么 W3 排第一个**：它最小（半天）、最疼（方寸自己的调用 50% 失败），而且是**两条线的共同前置** ——
架构图被驳回的真因就在这（`desktop.archGenerate` 2/2 `ok=false`，全是 JSON 解析失败）。
**为什么 W6 要早于 W5**：W5 会新增界面（进度条 / 取消按钮），不先冻结手搓，就等于"边迁移边加新债"。
**为什么 W4 可以和 W1/W2 并行**：它动 registry 与 CLI，不碰报表与看板；但它的"值不值"要用 W1/W2 的账来回答。
