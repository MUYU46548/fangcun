# 方寸 v0.4.1 交付流水线与运维评估

评估人：陆上线（部署运维）｜2026-10-24｜口径：Windows 11 单机桌面应用，无服务器

## 0. 结论

1. 这条链路**能出正确的包，但不能证明包是对的**。现在唯一的判据是"我跑过测试"和"命令退出 0"，两者都不可复核。
2. 最大的风险不是打包失败（失败会报错、会停），而是**发出去之后才发现**：`updater.ts:15` `autoInstallOnAppQuit = true` —— 坏包一旦上传，用户下次退出就装上，没有灰度、没有开关。
3. 三处"靠人记"的接缝里，**`release-<ver>` 拷回 `release/` 那处最危险**：它静默、无报错，而 `desktop/release/` 里躺着 9 组同名前缀的 exe，拷错没有任何东西会响。

## 1. 交付现状诊断

### 1.1 三个最大失败点（按 概率 × 影响 排序）

**P1｜没有统一门禁：测试靠人挑着跑，"跑过了"不可证伪**

- 证据：`desktop/package.json` 无 `test` 脚本；`scripts/test/` 下 68 个 `.cjs` + 9 个 `.py`；`.git/hooks/` 除 sample 外为空；AGENTS.md 里"全绿"的口径一天一个数（900 / 1041 / 1209 / 部分 SKIP）。
- 概率 100%（每次发版），影响 高。
- 真正的病灶是**判据本身不稳定**：EBUSY、需桌面会话、SKIP 三项在历史上反复漂移，"跳过"和"通过"在报告里长得一样。
- 放大器：坏包上线后用户退出即装，退回成本 = 用户自己去翻旧安装包。

**P2｜构建产物与发布取件是两个目录，中间靠手工 `cp`**

- 证据：`publish-release.sh:135` `REL_DIR = desktop/release`；构建输出是 `desktop/release-<ver>`（AGENTS.md:46，为绕 EBUSY）；AGENTS.md:54 明写"换输出目录再拷回"。
- `desktop/release/` 现存 0.3.4 / 0.3.5 / 0.3.6 / 0.3.7 / 0.3.8 / 0.3.9 / 0.3.10 / 0.4.0 / 0.4.1 共 9 组 `exe + blockmap`，770MB，文件名只差版本串。
- 概率 高（每次都要拷），影响 高。`release-precheck.py:136 check_assets` 只能证明"`latest.yml` 与 `exe` 互相自洽"——**把上一版这两个文件一起拷错，它照样通过**。
- 结论：这是"包里是上一版"最可能的真实成因，不是 electron-builder 的锅。

**P3｜`npm run build` 不查 `.vue`（无 `vue-tsc`）**

- 证据：`desktop/package.json:20` build = `sync-public-tools + vite build + tsc(main) + tsc(cli)`；devDependencies 无 `vue-tsc`。Vite 走 esbuild 转译，不检查类型。
- 概率 每次改渲染层，影响 中高。tsc 全绿而模板里 `undefined` 属性、错字 prop 直接进包；`verify.py` 与全部 `.cjs` 断言都碰不到（它们跑的是已编译产物，语法是合法的）。

### 1.2 已经修好的，不用再动

0.4.1 的"假成功"（本地领先 50 笔未推、`gh release create` 把 tag 打在远端旧 HEAD、脚本退出 0）已被 10-24 的两道闸堵住：`release-precheck.py` 前置体检（退出码 10–16）+ `--verify-release` 读回远端逐项比对 (`size` / `state` / `body` / `draft`)，配 39 条可测断言。这是这堆脚本里质量最高的一处，**保留原样**。

残留的唯一缺口：**两道闸都在 `publish-release.sh` 里，也就是跑在"包已经打好之后"**。包错了，闸只拦住不发，既不省工时，也不告诉你是哪一步错的。

### 1.3 "三个环境变量靠人记"算不算设计缺陷

算。但缺陷不在环境变量，在**它只存在于文档里**。判据很简单：这条知识有没有一个"必须执行"的载体？现在没有 —— AGENTS.md 是给人读的，新会话可能读，新机器可能没有。

它和 P2 是同一个病：**构建的输入（env、输出目录、镜像源）没有和代码一起被版本化**。

根治三条，成本都很低：

1. `build.electronDist` + `build.electronDownload.mirror` 写进 `desktop/package.json` 的 `build` 段 —— 这是 electron-builder 的正式配置键，写进去就永久生效、随 git 走，任何会话都不用记。【待确认】`ELECTRON_BUILDER_BINARIES_MIRROR` 是否有等价配置键；没有则由第 2 条兜住。
2. 打包入口从命令行改成脚本 `scripts/release.cjs`，剩余 env 在 `spawn(..., { env })` 里注入，人永远不需要看见它们。
3. 打包前**显式断言**：`node_modules/electron/dist/electron.exe` 存在，且其 `version` 文件 === package.json 声明的 electron 版本。不满足就停在第 4 步报错，而不是等 10 分钟超时或 502。

## 2. 构建可重复性方案

### 2.1 一条命令

```
cd desktop && npm run release -- 0.4.2
```

即 `node ../scripts/release.cjs 0.4.2`。**必须是 Node 脚本，不能是 bash**：npm 在 Windows 下用 `cmd.exe` 执行 scripts，`$PWD` 和反斜杠续行都不成立。零依赖，跨 cmd / PowerShell / Git Bash。

| 步 | 名称 | 动作 | 失败即停的判据 |
|---|---|---|---|
| 0 | 版本闸 | argv === package.json === skills/manifest.json === 发布说明首部；`docs/<ver>-发布说明.md` 存在 | 不等 → 提示 `npm run version:bump -- <ver>` |
| 1 | 清洁闸 | `git status --porcelain` 为空；`git rev-parse HEAD` 与 `origin/main` 同一提交 | 脏工作区 / 未推（离线则只警告，最终由 publish 的退出码 10 硬拦） |
| 2 | 构建 | `npm run build` + **`vue-tsc --noEmit`**（新增） | 任一非 0 |
| 3 | 测试 | `npm run gate:full`（含 `verify.py` + `drill-restore.cjs`） | 任一非 0 |
| 4 | 打包 | **先删** `release-<ver>/`；spawn electron-builder，`env` 注入三件套 + `--config.directories.output=release-<ver>` | 退出码非 0；打包前先断言 electron dist 版本 |
| 5 | 自检 | ① `Fangcun-Setup.<ver>.exe` 存在且 ≥ 80MB ② `latest.yml` 的 `version`/`size`/`url` 与实物一致 ③ 读 `win-unpacked/resources/app.asar` 头部，确认 `dist/main/boot.js` 在包内 ④ 跑 `win-unpacked/方寸.exe --version`，Node 主版本 === 由 electron 版本推导的期望值（44→24，**不写死**） | 任一项不符 → 停在第 5 步，**这才是"包里有新代码"的唯一证据** |
| 6 | 落位 | 三件套复制到 `desktop/release/`（同步取件目录，消灭 P2 的接缝），打印三个 sha256 | 复制后字节数必须与源一致，否则回头重新自检 |
| 7 | 交棒 | 打印一条可直接粘贴的 `bash scripts/publish-release.sh <ver>`；**不自动发布** | — |

设计要点：

- `--from=N` 断点续跑（打包 31 秒、全量测试 2 分钟，重跑整条很浪费）。
- 失败信息固定格式：`[第 5 步 自检] 失败：latest.yml size 116149519 ≠ exe 实际 79454986 → 说明 release-0.4.2/ 里混进了旧 exe，删目录重打`。**必须报出"是哪一步、为什么、怎么办"三件**。
- 发布仍然是"人按下去"的动作。脚本只到"把正确的包摆在正确的目录里"，审批点保留。

### 2.2 版本号三处一致：把"自动校验"降级为"结构上不可能不一致"

现状是三处（`desktop/package.json` / `skills/manifest.json` / `docs/<ver>-发布说明.md`）+ `latest.yml`（electron-builder 从 package.json 生成，天然一致）。判据已经存在（`release-precheck.py:124 check_versions`、`check-skills.cjs` 19 条里的一条），但只在发版那一刻跑 —— **漂移可以活几天，而它在发版时才爆，那时你已经打完包了。**

改法：

1. **唯一可写处 = `desktop/package.json` 的 `version`**，其余全部派生。
2. `npm run version:bump -- 0.4.2`：改 package.json → 改 `skills/manifest.json` → 从模板生成 `docs/0.4.2-发布说明.md`（含 `版本: 0.4.2` 与变更占位）→ 立即跑 `scripts/check-version.cjs` 自检。
3. `scripts/check-version.cjs`（新，纯 Node，60 行内）：argv === package.json === skills/manifest.json === 发布说明版本串；`latest.yml` 若存在则同值。**挂在两处**：pre-push 钩子（提前几天发现）+ `release.cjs` 第 0 步（发版时兜底）。
4. 结果：`release-precheck.py` 的退出码 14 从"第一道发现问题的关口"退化成"理论上到不了"的兜底。这才是自动化该有的位置关系。

## 3. CI 现实方案

### 3.1 硬约束（先摆事实）

- **Windows only**（REV-006）。GitHub-hosted `windows-latest` 是 Windows Server 2022，不是 Win11，**没有交互桌面会话、没有托盘**。`e2e-renderer.cjs`（真 Electron 真点击）在那儿跑不稳 —— AGENTS.md:119 已记录受限环境会 `RESULT SKIP`。
- 但**不需要桌面会话的那一层很大**：`tsc` main/cli、`vite build`、`verify.py`、以及全部用 `electron-stub.cjs` 的纯 Node 套件（约 50 个），云端可跑。
- 打包不适合上云：无代码签名证书；110MB 资产每次上传；`npmmirror` 是为国内网络挑的，Azure runner 上未必更快；tag / 版本号 / 发布说明仍要人工确认 —— 上云出包只是把人工挪了个地方。
- 自托管 runner 的硬伤是**物理性**的：跑在本机 = 和正在运行的 Electron 抢 `desktop/release*/win-unpacked` 里的 asar，正是那个 EBUSY 的成因。且单机无冗余，守护进程挂了没人知道。

### 3.2 不上 CI 时的最小可行边界

三层，按"必须跑"到"只是提醒"排：

1. **闸门 = `npm run gate`（本地一条命令）** —— 唯一可信的"跑过了"。
   - `gate:fast`（目标 ≤60s）：`check-version` + `tsc main` + `tsc cli` + `vue-tsc --noEmit` + `vite build` + 6 个静态守卫（ipc / bindings / buttons / themes / skills / ui-copy）。
   - `gate:full`：fast + 全部 `.cjs` / `.py` + `verify.py`，输出固定为 `失败 0 / 跳过 N`，**跳过项必须逐条列名**（不许只报一个总数）。
2. **发布脚本内嵌** —— `release.cjs` 第 1/3 步调它，`publish-release.sh` 保留现有两道闸。这样"发版一定跑过 gate"不依赖记性。
3. **pre-push 钩子 = 只跑 `gate:fast`** —— 纯粹的提醒。用 `git config core.hooksPath scripts/githooks` 装（`npm run hooks:install`），**不当闸门**：hooks 不入库、新机器要重装、`--no-verify` 一按就过。

### 3.3 推荐与被否决

- **推荐：`npm run gate` 本地闸门 + GitHub Actions 只跑 `gate:ci` 子集**（`windows-latest`，`npm ci` + tsc + vue-tsc + vite build + 纯 Node 断言；**不打包、不起 Electron**）。理由：公开仓库免费、成本≈0，防的是"改坏了没跑测试就推"；不承担发布，失败也不阻塞任何人。
- **否决：CI 出安装包。** 无签名证书、110MB 资产、镜像源不确定、tag 与说明仍需人工 —— 收益只有省 31 秒。
- **否决：自托管 runner。** 与 GUI 抢锁（EBUSY 有现成证据）+ 单机 + 常驻进程无人看管。
- **否决：把 `e2e-renderer`（真点击）塞进任何自动化。** 它要桌面会话，本机历史波动 294/12 → 298/8，SKIP 会被当成通过。正确做法是给它一个"发版前手工跑一次、把结果贴进发布记录"的位置（见 §5），而不是假装自动化了。

## 4. 数据安全与灾难恢复

### 4.1 通道不是太多，而是没有一条被验证过 + 职责重叠

现状：本地自动 zip（6h / keep 5 / `maxLocalMb=0`）、A WebDAV（`safeStorage` 存密码）、B 导出网盘同步夹、C 手动、restic（只生成脚本）、Git（镜像真实文件）。问题按严重度：

1. **除了一份录制在 `docs/恢复演练-20261018-173054.md` 的演练（16/0），没有任何通道有"最近一次成功"的可查记录。** `BackupState.lastSuccessAt`（`backup/config.ts:252`）字段已经存在，但通知门槛是 `failStreak >= N` —— "很久没成功过"和"根本没在跑"这两件事**都不会主动说出来**。备份最大的风险从来不是"没有备份"，是**"以为有备份"**。
2. restic 通道的红线（不注册定时、密码不进脚本）是对的，代价是**这条通道的实际成功率取决于用户有没有去挂 cron** —— 大概率没挂。它制造的是一种"看起来有备份"的错觉。
3. Git 通道的职责其实最独特（唯一能只回退一个文件、唯一可 diff），但现在被当成"又一条备份"在讲。

收敛建议 —— 保留 4 条 + 降级 2 条，每条只有一个职责：

| 通道 | 唯一职责 | 处置 |
|---|---|---|
| 本地自动 zip | **主力**：离线可恢复；恢复工具随安装包分发（`extraResources → tools/fangcun-restore.py`） | 保留，不动 |
| B 导出网盘同步夹 | **唯一异地**：零凭据、零服务端、用户已有网盘 | 保留，设为默认推荐 |
| Git 镜像 | **单文件回退 + 可 diff**：改坏一张卡时不必整包倒回 | 保留，文档里改定位（是"文件级时光机"，不是"备份"） |
| C 手动 | 兜底 | 保留（成本为零） |
| A WebDAV | 与 B 职责重叠，且是唯一要存凭据的通道 | **降级为高级选项**，不再默认推荐；代码保留（已用 safeStorage，风险可控） |
| restic | 与本地 zip 职责重叠，成功率最低 | **文档降级为"懂 restic 的人再用"**；说明里必须写出"不挂定时 = 这条通道不存在" |

比通道数量重要得多的一条硬要求 —— **新鲜度闸**：启动时算 `now - lastSuccessAt`，> 2×`intervalHours`（默认 12h）→ 设置页与托盘常驻红点，文案直说"最后一次成功备份是 X 小时前"。现有逻辑只覆盖"连续失败"，覆盖不了"根本没跑"。

### 4.2 恢复演练：从"跑过一次"变成"每次发版必跑一次"

`scripts/test/drill-restore.cjs` 已经支持真机零破坏模式（落到临时目录、真数据一字节不动），并自动落 `docs/恢复演练-<ts>.md`. 它缺的不是能力，是**一个必然发生的触发点**。

三层触发，不新增独立任务：

1. **发版前必跑**：`release.cjs` 第 3 步调 `node scripts/test/drill-restore.cjs`（用最新本地包）。发版频率 = 演练频率，退出码 1 直接停在第 3 步。
2. **每月一次**：启动时读 `docs/恢复演练-*.md` 最新一份的日期，> 35 天则提示"该演练了"并给一键入口。
3. **每次改 `backup/**`**：`gate:full` 已含 `e2e-backup`，把 `drill-restore` 一起加进去。

判据（沿用现有 16 条，冻结不改）：sha256 sidecar 通过 / 恢复文件数 > 0 / 任务卡计数 ≥ 备份点 / 逐字抽验 1 张卡非空 / 全部落在临时目录 / 耗时 < 30s。

结果落哪：`docs/恢复演练-<ts>.md`，并在 `docs/备份与恢复.md` 顶部钉一张"最近三次演练"表。**没出报告 = 没演练。**

### 4.3 升级安装（NSIS 覆盖安装）的影响面

会被碰：

- 安装目录 `%LOCALAPPDATA%\Programs\方寸\`（`perMachine=false`；用户改过路径按改的算）—— **整个目录被替换**
- `%APPDATA%\方寸\`（userData）：`data-dir.json`、`prefs.json`、`logs/`、`Cache/`。安装器不删，但这些都是**配置**，不是数据
- 开始菜单 / 桌面快捷方式、卸载注册表项

绝不会碰（安装器不知道它们在哪）：

- 数据根下的 `task-data/`、`registry.yaml`、`docs/`、`todos/`、`policies/`、`ideas/`、`notifications/`、`.backup/`、`backups/`
- 备份包 `backups/*.zip` 与 sidecar
- WebDAV 凭据密文（`backup-config.json`，安装不动它；密文绑 DPAPI 用户，换 Windows 账户解不开 —— 预期行为）

**唯一的真实危险配置**：数据目录被指到安装目录或其子目录里 —— 此时覆盖安装连数据一起替换。`data/index.ts:103 setDataDir()` 目前只校验"目标有没有 registry.yaml 或 task-data"，**不校验目标是否落在安装目录内**。建议加一条拒绝：目标路径命中 `path.dirname(app.getPath('exe'))` 前缀，或命中便携分支的 exe 同级（`data/index.ts:89`）→ 显式报错并说明原因。

卸载：`deleteAppDataOnUninstall` 未开 → 卸载不删 userData、不删数据根。**这句话必须写进文档**，否则用户会以为"卸载 = 干净"，反倒误删。

## 5. 发布检查单

贴进 `docs/<ver>-发布说明.md` 顶部，或单独一张卡，逐条打勾。

### 发布前

- [ ] `npm run version:bump -- <ver>` 三处同步，`git diff` 只有这三处 + 发布说明
- [ ] 发布说明写人话（不写"优化若干体验"），至少一句"这版修了哪个用户能感觉到的毛病"
- [ ] `cd desktop && npm run gate:full` → 失败 0，跳过项逐条过目
- [ ] `node scripts/test/drill-restore.cjs` → RESULT 16/0，报告已落 `docs/`
- [ ] （手工）`node scripts/test/e2e-renderer.cjs` 有桌面会话的机器上跑一次，把 `RESULT x/y` 贴进发布记录
- [ ] `git add -A && git commit -m "chore(方寸): <ver>" && git push origin main`
- [ ] `git rev-list --left-right --count origin/main...HEAD` → `0 0`
- [ ] `cd desktop && npm run release -- <ver>` → 8 步全过，第 5 步自检打出的 Node 版本正确
- [ ] 核对 `desktop/release/` 里三个文件的时间戳是**刚刚**（不是上一版留下的）

### 发布中

- [ ] `bash scripts/publish-release.sh <ver>` → 凭据段打印"✅ 有效，已认证为 <账号>"
- [ ] 前置体检全 PASS（若有 `--move-tag`，确认理由正当）
- [ ] 发布后复核打印三行 `<资产> <字节> uploaded`
- [ ] `gh release view v<ver> --json assets,body,isDraft` 人工看一眼：3 个资产、body 非空、`isDraft: false`

### 发布后（10 分钟内）

- [ ] **干净机器/干净用户目录实测安装一次**：装 → 启动 → 看版本号 → 关窗 → 托盘还在 → 退出

## 6. 回滚预案

| 触发条件 | 判定方式 | 执行步骤 | 预计耗时 | 验证方式 |
|---|---|---|---|---|
| 新版起不来（白屏 / 闪退 / 卡启动） | 干净机安装失败，或 ≥2 个用户报同一现象 | ① 手动跑上一版 `Fangcun-Setup.<old>.exe` 覆盖安装 ② 启动确认版本号 | 3 min | `方寸.exe --version` + 界面能起 + 卡片数不变 |
| 新版写坏数据（字段被清空 / 解析报错 / 卡片消失） | 发布后 24h 内出现同类报障 ≥1 例 | ① **立刻让应用停止写入**（关闭应用，避免自动保存继续覆盖）② 整个数据根 `cp -r` 到 `.quarantine-<ts>/` 取证，**不就地改** ③ 用 `.backup/` 单卡快照 或 Git 通道取回单个文件；整包恢复走 `fangcun-restore.py --target <临时目录>` ④ 临时目录与现场**人工比对后合并** ⑤ 降级到上一版 | 15–30 min | 任务卡计数 ≥ 备份点；逐字抽验 3 张卡；`verify.py` 全绿 |
| 资产传错 / 传残 | `publish-release.sh` 退出码 17 | ① `gh release edit v<ver> --draft`（**先让 `latest.yml` 对客户端 404，谁都不会装**）② `gh release upload v<ver> <正确文件> --clobber` ③ `gh release edit v<ver> --draft=false` | 5 min | 重跑 `python scripts/release-precheck.py . <ver> --verify-release MUYU46548/fangcun v<ver>` |
| tag 指错提交 | 退出码 13 | `bash scripts/publish-release.sh <ver> --move-tag` | 2 min | 脚本自己搬完再核一遍，打印新 sha |
| 版本号对不上 | 退出码 14 | `npm run version:bump -- <ver>` 后重打（**别手改某一个文件**） | 5 min | `node scripts/check-version.cjs <ver>` |

三条纪律：

1. **用户端回滚的唯一开关是远端 `latest.yml`。** 撤错包的动作顺序必须是"先让它不可见，再传正确的"。`--draft` 就是最干净的不可见（客户端读到 404 → 报错但不会装）。**绝不能先删 Release 再想** —— 用户那边会看到"找不到更新"，至少不装错，但你会失去 `downloadCount` 与资产元数据。
2. **数据库不存在，但"写坏数据"存在，而且比服务端更难查。** 格式不兼容的写入是静默的：卡片还在，字段空了。所以回滚预案的第一动作永远是"停写 + 取证"，不是"恢复"。取证目录留着，等新版修好再比对。
3. **`.backup/` 和 Git 通道是这里唯一能"只回退一个文件"的手段**，整包恢复会把备份点之后的好改动一起冲掉。这是它们不可替代的职责（见 §4.1）。

演练安排：

- 每次发版顺带跑 §4.2 的恢复演练（不需要额外日程）。
- 每季度手工跑一次**降级安装演练**：装 0.4.1 → 装 0.4.2 → 再装回 0.4.1，确认 `task-data` 卡片数与 `registry.yaml` 字节数不变。报告落 `docs/降级演练-<ts>.md`。这条现在从未验过。
