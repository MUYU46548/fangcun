## 三、两边的筛法（同一个口径）

| 筛子 | DSH | Hermes |
|---|---|---|
| 子 agent 会话 | `delegationDepth>0` 或 `parentSession` | `source='subagent'` 或 `parent_session_id` |
| 系统注入 | `runtime-context` / `time-context` / `goal` / `tool-jobs` | `[IMPORTANT: Background process …]` 等 |
| 伪装成 user 的东西 | 方寸交接日志（`## 上次执行日志…`） | **@ 附件上下文（整份代码粘进 user 消息）** |

**最后一条是 Hermes 独有的**：它会把用户 @ 的文件**整份**粘进 user 消息，形如

```
--- Attached Context ---
📄 @file:xxx.py (1647 tokens)
```python
…整份代码…
```
```

不裁掉的话，捞出来的"用户发言"里大半是**代码**，判定时会被代码里的词骗过 ——
和 DSH 那边「交接日志混进 user 消息」是同一类病。

## 四、这轮又踩的两个坑

### ① 会话 ID 全变成 `按会话（203 个）`

Hermes 产物用 `### ` 作会话标题、`## ` 作分组；而 DSH 产物用 `## ` 作会话标题。
解析器只认 `## ` → **667 条全挂在一个假会话下，cwd 全空** ——
项目分栏、`--project` 过滤**全部静默失效**，而输出看起来完全正常。

已改成两格式都认（`### ` 优先，`## 按会话` 视为分组跳过）。

### ② 判定器现在要能分辨"这条消息来自哪个产物"

加了 `--src` 参数。回归验证：DSH 侧判定**没有变化**（423 接住 / 12 / 9 / 106）。
