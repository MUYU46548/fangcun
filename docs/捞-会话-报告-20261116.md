## 二、技术坑：一开始以为"会话是空的"

这是本轮最值得记的一条，因为**它会让下一次捞取的人得出完全相反的结论**。

| 坑 | 后果 |
|---|---|
| **zstd 多帧拼接** | 一个 5 MB 文件里有 **3407 帧**。Node 的 `zstdDecompressSync` 和 `createZstdDecompress()` **都只解第一帧**，而第一帧只有 205 字符的会话头（`{"type":"session",...}`）。直接读 → **"这个会话没有任何内容"** |
| **解压顺序错了会静默失败** | 必须逐帧解：按魔数 `28 B5 2F FD` 找候选边界，逐段试解，解不开就扩窗（因为魔数字节也可能出现在数据里） |
| **`user/message` 里 82% 不是人说的** | 一个项目 2544 条 `user/message`，只有 208 条是真人输入 |
| **子 agent 的派工提示也是 `source:user`** | 「你是 Spec 轴评审员…」会被当成用户需求 |
| **方寸自己的交接日志被塞成 user 消息** | `## 上次执行日志…` 整段（含表格、代码）进了"用户发言" |

**所以做了三道筛子**（都写进了 `scripts/harvest-sessions.cjs`）：

1. **只留主会话**（`delegationDepth === 0` 且无 `parentSession`）→ 排除子 agent 派工
2. **只留 `source.kind === 'user'`** → 排除每轮重发的 `runtime-context` / `time-context` / `goal` / `tool-jobs` / `skill-catalog`
3. **排除注入型**（`## 上次执行日志` / `<system-reminder>` / `Goal` 等）→ 排除方寸自己写的东西

三道的效果：**2544 → 208**（方寸）· **626 → 550**（全部，另 76 条注入）。

## 四、这份东西能干什么（也是它唯一的价值）

**它把"消失的需求"变回了可检索的文本。** 举个刚捞到的原话（方寸，10-31 那批）：

> 「这个是什么意思？能不能简单告诉我这个功能怎么用？和决策有什么区别（**决策依然缺乏写入，没有用活**）」
>
> 「我狂点通过但是一点视觉回馈都没有，一直挂在那里，很夸张。我只能尝试把每个都点了，而且根本分不清哪个点过了哪个没点。」

**这两句在 139 张未完成卡里没有对应卡。** 也就是说：用户说过、当时没做、也没有任何记录 —— 只有会话里有。

这正是"上千处"的形状：**不是卡里漏了，是从来没进过卡。**

1. **没做"已做/未做"判定** —— 550 条里哪条已被卡接住、哪条彻底没人管，需要逐条比对卡与提交，工作量比捞取大一个量级。

4. **没动任何会话文件** —— `harvest-sessions.cjs` 只读。
