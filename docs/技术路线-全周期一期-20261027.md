## 抉择一 · 外部 agent 的工具，还是内置 agent？

### 判断：**外部 agent 的工具。方寸做「料」和「口」，不做「脑」。**

| 依据 | 实测/原文 |
|---|---|
| 能力差是数量级的 | 内置那条直路（`writeback.ts:157`）输入只有 **4639 tokens 的标题级摘要**、59 秒、产出 7 张平铺卡；外部 agent 能读全正文、能多轮、能被否了重来 |
| 成本方向相反 | 内置：每次花你的钱，产出没人用；外部：已订阅，边际成本 0 |
| 契约精神 | REV-007 原话「**方寸是地图不碰执行引擎**」——推理就是执行 |
| 可替换 | 外部 agent 三个月换一代，方寸跟着换；内置锁死在一家模型上 |

**这不是回到 003 卡的 B 方案。** B 被否的理由是「产物无处安放」——REV-008 之后有地方放了（1+2 的两个对象）。B 复活，但必须改掉一个致命点：

> **回填必须是机器做的，不是人粘 md。** 003 卡自己写了 B 的代价是"多一步导出/回填"——那一步就是它一定不会被用的原因。

### 形态：两端各一个接口

```
方寸 ──出料──▶ 外部 agent（我 / Hermes / DSH）
  ▲                    │
  └──── 结构化回填 ─────┘   ← 落「待审批」对象（REV-005 边界②仍生效）
```

- **出料**：`get_definition_context(project)` / `get_plan_context(project)`，走已有 MCP 通道
  （方寸现成 27 个 MCP 工具那一套）。内容复用 `main/services/contextPack.ts`（270 行，10-22 已有雏形），
  按 1+2 两段各自的信息需求重组。
- **回填**：`submit_definition(draft)` / `submit_plan(draft)` —— 只收**固定 schema**，
  **一律落「待审批」**，用户点头才转正。格式不对直接拒收，不做宽松解析。

### 走错的样子

- ✗ 方寸里出现「一键生成规划」按钮，内部直接调 LLM 出终稿 → **这是抉择二的 L2，不做**
- ✗ 回填靠人手工粘 md / 上传文件 → **摩擦太大，一定不会用**（B 被否的原因）
- ✗ 让方寸自己决定"该问外部 agent 什么" → 又变成内置编排

## 抉择二 · 接入 LLM 多深？

### 判断：**L0 为主 + L1 少量 + 不做 L2。**

| 层 | 做什么 | 判定 |
|---|---|---|
| **L0** | 零 LLM：容器、结构校验、缺口报告、双向覆盖、几何/结构断言 | ✅ **主体** |
| **L1** | 读/抽/归类/校验 —— **只搬事实，不发判断** | ✅ 少量，四处 |
| **L2** | 直接生成定义或规划 | ❌ 现在不做 |

**L2 不做的三条依据（不是保守，是算过账）**

1. 003 卡实测：L2 在 S2（内容可用）上概率约 **30%**，且今天那 7 张卡是"复述你的话"。
2. 004 卡铁律：任何数字必须自带「它证明不了什么」。**L2 的产出没有客观判据 → 不可审计**，
   而"不可审计的建议"正是你两次打回的那类东西。
3. **安全边界（这是你问的重点）**：L2 要把整个项目正文（fangcun 未完成卡 3.4 万字）一次性发出去；
   L1 只发**局部**（一张卡、一段文本），**暴露面小一个数量级**。BYOK 解决的是"发给谁"，不是"发多少"。

**L1 的四个用途（全部可被人一眼核掉）**

| 用途 | 输入 | 输出 | 为什么不用 L0 |
|---|---|---|---|
| 抽取：这条日志实际改了什么 | 单条日志/结果记录 | 事实清单 + 原文位置 | 自然语言，正则做不了 |
| 聚类：返工原因归类 | 30+ 条自由文本 | 类别 + 成员 + **可推翻** | 类别必须后出（004 卡已定） |
| 覆盖检查 | 需求 ↔ 任务 | 缺哪边 + 位置 | 判"这两句是不是同一件事"需要语义 |
| 格式校验 | 外部回填的 draft | 合规 / 具体哪条不合规 | 用 L0 即可，**此处不需要 LLM** |

### 走错的样子

- ✗ **L1 的输出里出现「建议 / 应该 / 优先级 / 更重要 / 推荐」→ 越界，退。**
  L1 的输出必须全部是「事实 + 位置」（哪张卡、哪一段、原文是什么）。
- ✗ 某个功能说不清它是 L0 还是 L1 → 按 L2 处理，不做。
- ✗ 为了"效果更好"偷偷把正文全塞进去 → 违反上面第 3 条，属于安全边界变更，须重新拍板。

## 抉择三 · 产物形态：卡，还是可视化方案卡？

### 判断：**先定 schema，再定视觉。顺序反了就是给列表换个皮。**

003 卡的核心诊断就是这一条：**输出 schema 里没有「规划」这个形状** —— JSON 里没那个字段，
画出来只能是 7 个平铺方框。所以视觉不是设计问题，是数据形状问题。

### 第 1 段「定义」的 schema

```js
{
  为谁:      string,          // 一句话
  解决什么问题: string,        // 一句话
  不做什么:   [{ 项, 理由 }],  // ★ 必须有，且是数组不是一句话
  能力边界:   [{ 边界, 理由 }],
  需求:      [{ 表述, 验收判据, 关联卡[] }],
  状态:      '待审批' | '已确认',
  来源:      'human' | 'agent:<名>'
}
```
**「不做什么」是显式字段而不是文档里的一句** —— 取舍的载体在这里，不在正文里。

### 第 2 段「规划」的 schema

```js
{
  主线: [{ 段名, 目标, 验收判据, 卡在谁, 涉及卡[] }],   // 有序
  依赖: [{ from, to, 理由 }],                          // 谁挡着谁
  砍掉: [{ 候选, 理由, 何时可能捡回来 }],               // ★ 最关键的字段
  不动: [{ 候选, 理由 }],                              // 明确划出去的
  状态: '待审批' | '已确认'
}
```
**没有「砍掉」和「不动」的规划不是规划，是清单。** 这两项是 003 卡指出的"缺的形状"的核心。

### 视觉形态（跟着 schema 走，不自由发挥）

| 段 | 一屏长什么样 |
|---|---|
| 定义 | **一页，不是列表**：左「为谁 / 解决什么」，右「不做什么 / 边界」，下方需求条目（每条带验收判据 + 关联卡数） |
| 规划 | **一条纵向主线**（现在 → 下一个可验收点），依赖画成分叉线；**「砍掉」放右侧独立窄栏**，视觉上必须与主线分离 |

### 走错的样子（结构判据，可写成断言）

> **把颜色和框线全去掉，如果剩下的还是一堆平铺条目 —— 它不是规划图，是列表换了皮。**

- ✗ 「砍掉」和主线混在同一个列表里 → 不算
- ✗ 需求条目没有验收判据 → 不算（那就回到"看不懂的卡"）
- ✗ 定义页变成一段 markdown 长文 → 不算

## 十几项分支：哪些现在必须定，哪些可以先给默认

### 必须现在定（改了要迁移数据）

| # | 分支 | 初判 |
|---|---|---|
| 1 | **数据存哪** | 沿用现有 policy 管线的同类做法（markdown + frontmatter，与卡同根），**不引 sqlite**。理由：零依赖是选型定死的 |
| 2 | **对象 ↔ 卡的关系** | 需求 `1 : N` 卡（一条需求挂多张卡）；**卡只能挂一条需求**（多挂即来路不明） |
| 3 | **一个项目几份定义** | **一个项目一份「当前定义」+ 历史版本归档**。不并行多份（并行 = 立刻需要选择器 = 立刻看不懂） |
| 8 | **与现有方针卡（policy）的关系** | **两层，不合并**：方针 = 长期使命/目标/边界；产品定义 = 当前版本的具体形状。⚠ **界面上必须明说这两块的区别**，否则就是两块像的东西并排 |

### 可以先给默认、以后改

| # | 分支 | 默认 |
|---|---|---|
| 4 | 外部回填与人工修改冲突 | 回填只进「待审批」，**永远不覆盖已确认**；冲突时并列给人看 |
| 5 | 待审批对象与待审批卡是否同一队列 | **同一队列**（一处点完），但分类型标识 |
| 6 | 视图放哪 | **不许新开第五个页签**（见下方硬要求） |
| 7 | 多项目切换 | 复用现有项目选择器 |
| 9 | 定义/计划的版本与归档 | 每次「已确认」存一版，可 diff |
| 10 | 导出格式 | 给人看的 md + 给 agent 的 JSON，同一份源 |
| 11 | 撤销 | 复用现有 undo 机制 |
| 12 | 怎么知道没人用 | 复用 `mcp-usage.jsonl` 那套读卡计量，**对象也计进来** |

### ⚠ 一条硬要求（直接冲着你「看不懂所以不用」来的）

**第 1、2 段不许新增一个"看起来像现有视图"的独立页面。**
必须是一条线：**定义 → 计划 → 卡**，三段连着，从上往下走。
否则方寸就变成"第 N 个没人看的页面"——那正是它现在的问题，不能再用同样的方式加一遍。

## 最后：回答你那句「方寸本来就应该做这个，但是现在做不了」

**对，它做不了。而且按这条路走，它以后也不做这个。**

刚才定这三条路线靠的是：读契约、读两张卡、跑 git、翻日志、判断你的偏好——**这些数据方寸全都有**，它就摆在手上。

它缺的不是数据，是**一个能读完这些、被否了还能改、连着聊三轮的位置**。那是 agent，不是方寸。

**所以方寸在这件事上的职责不是替你想，是不让你在错的信息上想** ——
比如它今天本该直接告诉你：「registry 说司天 M1 未起，实际 30 天 187 次提交」。
这一条比"帮你生成一份规划"有用得多，而且是它真做得到的。

## 这份路线证明不了什么

1. **三个抉择的依据全部来自方寸自己的实测**（003/004 卡），没有一个外部对照。如果那两张卡的实测有偏差，结论跟着偏。
2. **我没估工程量。** 第 2 段的"主线 + 依赖 + 砍掉"要新视图，这块一定比全部后端加起来大（003 卡原话）。
3. **"L1 只发局部"是我的设计，没做过安全评估。** 如果以后有功能需要发全文，那是另一次边界变更，得重新拍。
4. **分支 12 项只是初判。** 第 4、6、9 项我给了默认，不代表它们对，只代表现在不改也能走。
