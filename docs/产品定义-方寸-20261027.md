## 为谁

**当前是一个人（暮雨）。以后要给别人用。**

一期按一个人做对：六个在途项目，从写小说到画地图到做看板，全部自己写代码。

⚠ **但数据模型不许假设只有一个人** —— `验收` 是字段不是常量「暮雨」；「成员」沿用 registry 已有的 `members`。
一期不做权限/协作/评论，**但也不许把"单人"焊进 schema**，否则以后给别人用要迁移全部数据。

## 解决什么问题

**信息都在手上，但拼不起来。**

具体到能摸到的三个场景：

1. **要判断"先动哪个项目"，得挨个翻目录。** 六个项目的进度写在 `registry.yaml` 三句话里，
   而今天实测那三句话**五条是过期的**（司天写着"施工未起"，实际 30 天 187 次提交）。
   判断建立在过期地图上 —— 这是"规划做不出来"的机械原因。
2. **172 张待办，说不清哪张该先做。** 因为它们全都"一样新"，没有上层依据（为谁/不做什么）可供排序。
3. **"做完了"没有证据。** 卡上只有一个「验收人：暮雨」，没有"谁凭什么验的"。

## 不做什么（这一节比上面重要）

| 不做 | 理由 |
|---|---|
| **代码编辑器 / IDE / CI** | 有 VS Code 和 git，不重造 |
| ~~**需求管理系统（Jira 那类）**~~ | **反转：要做。**（暮雨 2026-10-27 21:55：「需求管理系统明显是一个好方向」）理由见下方「突破点」——它不是"又一个功能"，是投入产出对照的锚点 |
| **团队协作 / 权限 / 评论** | 一期不做。但 schema 不假设单人（见「为谁」） |
| **内置 agent 编排（并行执行）** | 契约排除项；外部 agent 更强且已订阅 |
| **替用户做判断** | 工具一旦"加权决定什么更重要"，就是替人做价值判断 |
| **要求用户往里写内容才能用** | 见下方「边界」最后一条 —— 这是历史教训 |

## 能力边界

- **对项目仓库只读**，不写别人的仓库（契约 ③）
- **不监听外网**，只有本机回环看板端口
- **LLM 只在用户自填端点下工作**（BYOK），产出只落「待审批」，花销可见
- ⚠ **最硬一条**：方寸至今唯一被真用的是日志 —— 因为日志是 **agent 写、它只展示**。
  凡是要求用户写东西才能用的（93 张待办、74 张 10-15 批量导入的卡），一件都没活下来。
  **所以任何新能力，用户在生产环节的投入必须为零，只保留"点头/否"。**

## 突破点：让「白费」可见

> 暮雨 2026-10-27 21:55：「**今天方寸救不了自己，靠外部 agent 也救不了自己，关键在于找到那个突破点，
> 让 token 不在错误的路线上继续白费**（比如我今天否掉的一大堆东西，实则节约了大量成本）。」

### 先说清为什么"加强规划"不是突破点

两条路都是空转，因为**输入输出是同一个闭环**：

- **方寸规划自己** → 输入是它自己写的卡和日志 → 输出只能是整理
- **外部 agent 规划方寸** → 我读的也是它写下来的东西 → 同样只能是整理

003 卡已经算过这笔账：「数学上不可能产生你不知道的事」。所以**换模型、换 schema、加轮次，得到的都只是"更漂亮的复述"。**

### 那新信息在哪：只有方寸同时握着「花了多少」和「得到了什么」

| 数据 | 方寸 | 外部 agent |
|---|---|---|
| `ai-trace.jsonl`：每次调用 + token 花销 | ✅ 全量 | ❌ 只看得到当前会话 |
| 卡的状态跃迁（谁从待办变完成、变了多久没动） | ✅ | ❌ |
| git 提交（哪天真的动了代码） | ✅ 只读可得 | 部分 |
| **被否掉的提案 + 否掉的理由** | ❌ **完全没有这个对象** | ❌ 一次会话结束就没了 |

**这就是突破点的位置**：任何单个会话看起来都很努力，**只有跨会话、跨项目横着看，才知道哪条线在空转**。

### 判据压成一句话

> **过去 N 天，这个项目花了多少 token，产出了几件"真的被用起来"的东西？**

「真的被用起来」= 验收通过 / 被合并 / 已发布 / 被别处引用。**不算「卡变完成」**——那是自报（004 卡的证据门）。

### 为什么需求管理从"不做"翻成"要做"

因为**没有需求就没有锚点**，投入产出这条链根本算不出来：

| 问题 | 没有需求时 | 有需求时 |
|---|---|---|
| 这笔 token 花在哪 | 只能记在"某个会话"上，无法聚合 | 挂到需求上，可累加 |
| 这算不算做完了 | 只能看卡状态（自报） | 需求有验收判据 |
| 规划该砍什么 | 只能砍卡 | 能砍需求（卡的上级） |

**所以需求不是"又一个功能"，它是这个分数的分子。** 这也是为什么它跟"全周期"第 1 段是同一件事。

### 今天这一整天，就是第一份样本

被否掉的方向，每一条都是白费的 token：

| 被否的 | 理由 | 成本 |
|---|---|---|
| SDD 状态层（八家调研 + 一份文档） | 看不懂 / 不会用 / 达不到 | 一整轮 + 一份文档 |

| 我先拍了一套 schema | 预设形状 | 上一轮 |

**这些如果只留在对话里，明天我还会提一遍。** 记下来，才是真的"不再白费"。

## 需求（每条带验收判据）

| # | 需求 | 验收判据（可机械判定） |
|---|---|---|
| **R1** | **「白费」可见（一期主线）** | 给定时间窗，能报出：花了多少 token ／ 产出几件「真被用起来」的（验收通过·合并·发布·被引用）／ 几件提案被否 + 理由。**任一格取不到就不显示整格，不许填 0 或「—」** |
| **R2** | **需求作锚点（一期主线）** | 每条需求有验收判据，且能把卡、token、提交挂到需求上。**存在挂不上任何需求的卡 → 必须计数并列出** |
| R3 | **状态不许过期** | 每个项目的「当前进度」要么来自 git 实测，要么显式标出「上次核对：日期」。**存在未标核对时间的进度描述 = 不合格** |
| R4 | **让"对不上"可见** | 定义说要做但没卡的 → 列出；有卡但不在定义里的 → 列出；待办挂不上需求的 → 计数。**空集必须显式说"没有"，不能白屏** |
| R5 | **规划有形状** | 出的规划必须含「顺序」「依赖」「**砍掉什么**」三项。**只有条目的不叫规划** |
| R6 | **不要求用户写** | 定义与规划由外部 agent 产出，用户界面里只有「点头 / 否 / 改一句」。**出现"请填写"表单即不合格** |
| R7 | **数字自带局限** | 每个数字旁边有「它证明不了什么」。**只有数字没有局限说明 = 不合格**（反例断言：删掉局限 → 精确红） |

## 正式版门槛（暮雨 2026-10-27 21:52 定的验收）

> 原话：「**什么时候方寸能做好自身的规划，才算可以拿出去发正式版**。」
> 同日 21:55 补：「**方寸救不了自己，靠外部 agent 也救不了自己，关键在于找到那个突破点**」。

⚠ **这两句合起来才有意义**：门口写着"能规划自己"，但**通往门口的路不是加强规划，是先让它能看见自己的白费**。
否则第 2 条那个"规划"还是复述 —— 因为它的依据仍然只有自己写的卡和日志。

译成四条，**四条同时成立**才算：

1. 方寸有一份**你点头过**的、关于它自己的产品定义（就是这份的定稿）
2. 方寸基于这份定义 + **投入产出账**（花了多少 / 产出了什么 / 哪几条被否），出一份下一版规划
3. 那份规划含顺序、依赖、砍掉什么，且**你不用改就能拿去派活**
4. **至少有一条是从投入产出数据里算出来的、你原来不知道的** ——
   不是"全新想法"（数学上不可能），是"**这些数字摆在一起才看出来的事**"，
   典型形态：某个方向花掉了大部分 token 却零验收产出；某条提案已经被否过两次。
   **这一条做不到，就还是 003 卡说的"更漂亮地复述"**。

## 这份定义自己承认的局限

1. **「给别人用」我采纳了，但一期没有为第二个人做任何设计。** 只留了一条约束（schema 不假设单人）。
   这是不是够，我不知道 —— 如果不够，就要在 0.6.0 之前补，而不是等真要给别人用的那天才发现。
2. **「白费可见」这个突破点是我的判断，不是你的原话。** 你的原话是"找到那个突破点"，
   我把突破口定位在投入产出上。**如果真正的瓶颈不是白费而是别的（比如你根本不想看数字），整节作废。**
3. **需求管理翻成"要做"，风险明摆着**：它极可能变成"第 94 张待办"。
   能不能守住，全看 R6（不要求用户写）——**需求得由外部 agent 起草，你只点头**。
4. **七条需求的验收判据全是"结构可判"，不涉及"好不好用"。** 好用只能等你用过之后说。
