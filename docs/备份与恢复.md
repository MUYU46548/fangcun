# 方寸备份与恢复

> 本文档说明方寸的备份能力边界、上云路线选择、校验与恢复步骤，以及责任声明。

## 一、备份内容与边界

| 项目 | 说明 |
|---|---|
| **纳入** | `task-data/`（全部任务 Markdown）、`registry.yaml`（项目登记）、`docs/`（执行日志等） |
| **不纳入** | 代码、`git` 历史、`node_modules`、`Cache/`、`.trash/` |
| **永不纳入** | `llm-config.json`、`backup-config.json`、`apps.json`、`credentials.json`、`.env`、`*.key`、`*.pem`、`*.p12`、`*.jks` |
| **格式** | 单个 ZIP 包 + `.sha256` 校验文件 + `.manifest.json` 逐文件清单 |
| **大小** | 全量数据约 100 KB 级（压缩后 85 KB 左右），无增量包 |
| **加密** | **不加密**。包内是任务数据的完整明文 |

密钥被排除是硬约束：每次备份的 `manifest.json` 里 `excludedSecrets` 字段会列出本次实际排除了哪些敏感文件，便于审计。

## 二、上云的三条路线

### 路线 A：WebDAV 直连（方寸内置，全自动）

适用于**支持标准 WebDAV 的服务**：自建 NAS（群晖/威联通）、Nextcloud、Seafile、坚果云（见下）。

设置页 →「备份与恢复」→ 填 WebDAV 地址/账号/密码 →「测试远端」通过 → 保存。
之后每次自动备份会同时上传，并在上传后核对远端文件大小，确认未被截断。

> **坚果云补充**：坚果云已收紧了应用密码的生成入口，且 Windows 客户端默认全量同步。
> 若无法拿到应用密码，建议改用路线 B。

### 路线 B：导出到网盘同步文件夹（推荐，最可控）

**原理**：方寸只管把备份包写到本地某个目录，上传由你已在使用的网盘客户端负责。

设置页 →「备份与恢复」→「存放目录」填网盘同步文件夹路径 → 保存。
此后自动备份直接落在该目录，客户端自动上传。

或使用「📤 导出到…」按需导出一份到任意位置（U 盘、NAS 挂载盘、临时目录）。

**这条路线的优势**：
- 不接触任何第三方 API，不需要申请应用、不需要 OAuth、不需要维护 token
- 不存在"方寸把密钥泄露给云服务"的可能
- 断网、客户端离线都不影响本地备份的可用性
- 换任何网盘都能用（OneDrive / 坚果云 / 百度网盘 / 阿里云盘 / 群晖 Drive）

**关于"客户端会占满本地空间"的顾虑**：
方寸的备份包只有 ~85 KB，即使保留 10 份也不足 1 MB。
而现代网盘客户端（OneDrive「文件按需」、坚果云选择性同步）默认不会主动下载未访问的文件。
如果确实想节省空间，可在客户端里把备份子目录设为"仅在线"，或用完即手动清理。

### 路线 C：完全手动

「📤 导出到…」→ 选目录 → 拿到 `zip + .sha256 + .manifest.json + README.txt + fangcun-restore.py` →
自己传到任何地方。

推荐用于：临时迁移、给别人交接、放离线冷备介质。

## 三、OneDrive 为什么不能走 WebDAV

**结论：OneDrive 个人版不提供标准 WebDAV 接口，方寸无法直连，也不建议绕。**

- 微软从未为**个人版** OneDrive 提供官方 WebDAV 端点。早年 SkyDrive 时代的 `d.docs.live.net` 属于已废弃的旧 API
- **OneDrive for Business**（SharePoint Online）在特定路径下曾支持 WebDAV，但需要企业/教育账号，且行为与服务端策略绑定
- 第三方工具（rclone / AList 等）把 OneDrive 挂成 WebDAV 的做法，本质是**自建代理做协议转译**，不是官方能力。
  这种方案在并发写入场景下有已知风险：OneDrive 底层 API 不提供 WebDAV 依赖的 `LOCK`/`UNLOCK` 语义，
  转译层无法保证原子性——对备份文件这种"写坏就白备"的场景尤其不合适
- 微软自 2024 年 6 月起收紧了个人账号的应用注册策略，自行申请 API 凭证做直连的门槛进一步升高

**所以**：如果要用 OneDrive，就走**路线 B** —— 让 OneDrive 客户端同步你已经生成好的备份包。
这既绕开了全部鉴权问题，也比协议转译更可靠。

> 若将来确实需要直连 OneDrive，唯一官方路径是 Microsoft Graph API（OAuth 2.0 + Azure 应用注册），
> 需要单独实现授权流程、token 刷新与安全存储，并另附免责声明。当前不建议为"备份"这个需求付出这个成本。

## 四、校验

任何一份备份包在**恢复之前**、或在**从网盘下载回来之后**，都应先校验。

**方式一：方寸应用内**
设置页 →「🔍 校验备份包…」→ 选择 zip → 显示结论、备份时间、文件数、失败原因。

**方式二：独立工具（可脱离方寸）**
把 `fangcun-restore.py` 与备份包放在一起，任何装了 Python 3.8+ 的机器都能用：

```bash
python fangcun-restore.py verify  fangcun-data-YYYYMMDD-HHMMSS.zip
python fangcun-restore.py list    fangcun-data-YYYYMMDD-HHMMSS.zip
```

校验分四层，任一层不过即判定失败：

1. `sha256` 与随包的 `.sha256` 文件比对
2. ZIP 结构可解析 + 逐条目 CRC 校验
3. 每个条目的 local header 与 central directory 字段交叉比对
   （防止"只改一处、骗过部分解压器"的篡改）
4. `manifest.json` 自洽：条目齐全、文件数吻合、抽样复核逐文件 sha256

## 五、恢复

**方式一：方寸应用内**

「📥 从文件恢复…」或备份列表中的「恢复」。流程：

1. **校验**——不通过直接中止，不动任何数据
2. **解压到临时目录**——确认包内确有 `task-data/`
3. **快照现有数据**——整体改名为 `_restore-snapshot-<时间戳>`
4. **原子替换**——把还原内容移入数据目录
5. **失败自动回滚**——从快照还原回原状

**方式二：独立工具**

```bash
python fangcun-restore.py extract fangcun-data-YYYYMMDD-HHMMSS.zip D:\恢复到这里
```

校验不过时工具会拒绝解压。还原后把 `task-data/` 与 `registry.yaml` 放回方寸数据目录即可
（默认 `%APPDATA%\fangcun-desktop`）。

**恢复后必须手动重填**：LLM 配置（API Key / Base URL / 模型）、WebDAV 配置。
这两项含密钥，不在备份包内——这是有意设计，不是缺陷。

2. **备份包未加密**。包内为任务数据的完整明文。因备份包泄露、误传公开位置、分享给他人、

3. **云端副本不受方寸控制**。上传后文件由第三方网盘/WebDAV 服务存储与传输。方寸仅在上传完成时
   核对过一次文件大小，此后无法感知云端是否被改动、删除、限流或静默损坏。**建议定期用
   「校验备份包」抽查从云端下载回来的副本。**

4. **恢复操作会覆盖现有数据**。虽然流程内置快照与失败回滚，但快照仅在恢复流程正常结束时清理；

   **执行恢复前请先另存一份当前数据。**

5. **自动备份依赖应用运行**。定时备份仅在方寸进程存活时触发。应用未启动、机器关机、
   系统休眠期间不会产生备份。请勿将自动备份视为"设好就不用管"的保障。

6. **密钥不在备份内**。恢复后 LLM 与 WebDAV 配置需重新填写。同理，若你遗失了原始密钥，
   方寸无法从备份中恢复它。
