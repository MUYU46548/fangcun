## 0.5 订正（同日 13:0x，暮雨「总觉得哪里不对劲」之后自查）

**他感觉对。这份方案有四处毛病，第四处是致命的。**

**① 我把自己的判断包装成了「已定」。**
§0 那张"已定"表里，`ADR-001`、`产品定义 R1/R2` 都是**我起草的**，产品定义文件头自己写着
「这是第一份手写样本……**你否掉它就是它的价值**」，局限 §2 更写明「**「白费可见」这个突破点是我的判断，不是你的原话**」。
用"每条标出处"提高了可信度，但出处全是我自己的文件 —— 这比编造更难被发现。
→ **真正"已定"只剩六条**：契约 REV-005/006/007/008 · 你 10-27 21:52 与 21:55 两句原话 · 10-16 九条 · 10-24 三连裁决。
其余全部改成「我提议」。

**② 需求做起点是错的，我自己警告过。**
产品定义局限 §3 原话：「需求管理翻成'要做'，风险明摆着：**它极可能变成'第 94 张待办'**」。
我却把它设成 M1 的起点 —— 那是往一个已经堵住的队列里再灌东西。

**③ 净增复杂度。** 12 视图移出 4 个、新增 2 个页签 + 8 类机检 + 1 对象 + 2 写口 = **净增**。
他的问题是"30 天只有日志能用"，再加只会更没人用。→ 见第 ④ 条之后的修正。

**④ 致命的：「待审批」是一个没有出口的队列，而我的 M1/M2 都在往它里面灌。**

实测（`task-data/*.md`，`来源: ai-planning`）：

| 调用 | 时间 | token | 产出卡 | 现在状态 |
|---|---|---|---|---|
| draftProjectBrief（ROSA） | 10-17 08:10 | 无 usage | 1 | 待审批 |
| planToDraft | 10-22 12:14 | 10,686 | 5 | 全部待审批 |
| draftProjectBrief（方寸） | 10-24 02:45 | 6,368 | 1 | 待审批 |
| planToDraft | 10-27 11:14 | 8,538 | 7 | 全部待审批 |

**累计 4 次调用 / 25,592 token → 14 张卡，零张转正、零张被否。**
而且其中 10-22 那 5 张（W1 地基验收 / 两份评估报告 / 规划上下文包 b 版 / 模型通道合规 / 链路干跑自检）
**不是垃圾，是真待办** —— registry 的「说明」里还写着同样的话（"欠着：②W1 地基已落待你验收 ③两份评估报告 ④上下文包 b 版"）。
**同一件事在 registry 和卡里各说一遍，两边都不动。**

→ **真因不是"判据缺失"，是「待审批」没有出口。** 记了以后没有任何机制把它推到下一状态，
于是"方寸记不住"的机械形态就是：**记了，但卡在一个没人经过的门口。**

→ **修正三条（比原方案小得多）**：
1. **给待审批开出口**：超过 N 天没人动 → 自动降级（不删、不阻挡，计入"被否/过期"），
   而不是永远等。这才是「有对象，没门禁」的正解 —— 不阻挡，但也不静默堆积。
2. **不许两处各说一遍**：mismatch 增一类 —— registry「说明/状态」里提到但库里无对应卡的，反向也抓。
3. **R1 白费账先解决口径**：`ai-trace.jsonl` **只记方寸自己调的**（5 条 / 25,592 token / 10 天），
   外部 agent 的花销一条都不进。所以 M3 若照原样做，会报出一个比真实小三个量级的数 —— **比不报更糟**。
   要么 MCP 加一个 usage 上报口，要么按 R7 明说"这个数只覆盖方寸自己调用，占真实花销的极小部分"。

**⑤ 并且，今天四份文档、零行代码。** 这是 ADR-001 自己写下的失败条件（"这份仍然是文字"）。
下一步必须是代码或清理，不能再是文档。

## 1. 一句话定位（可对外说人话的版本）

> **方寸 = 一个能自己回答三句话的本地账：哪件事值得做、这件事做完没做完、钱花得值不值。**

三句话对应三个已有定义，不是新增：
- 哪件事值得做 → 规划段（R5：含顺序/依赖/砍掉什么）
- 做完没做完 → 定义段的 AC/DoD（本方案第 4.3 节）
- 钱花得值不值 → R1 白费可见

## 2. 主干：**只有一条闭环**，别的一律挂在这条上

```
  需求（US + AC）          卡（任务）            提交 / token
  task-data/               task-data/            git + ai-trace.jsonl
  requirements.md          *.md
        │                      │                       │
        └──────────┬───────────┴───────────┬───────────┘
                   ▼                       ▼
            ①挂得上吗？              ②产出真的被用了吗？
                   │                       │
                   └──────────┬────────────┘
                              ▼
                       白费账（R1）
                              ▼
                     规划（顺序/依赖/砍掉什么）
                              ▼
                     派活（tegula next）
                              ▼
                   收单机检（对不上 · 8 类）
                              ▼
                     ┌───────┴───────┐
                  合格              不合格
                     │                 │
                  完成留痕          红标打回（带 diff）
```

**这条闭环的每一段都有宿主、有写者、有判据**（第 4、6 节给到字段级）。没有宿主的东西不进方案。

**为什么只有一条**：ADR-001 的症状是"没有一个对象承载当前判断"。一条闭环 = 一个承载点。多一条闭环就是多一个要维护的判断源。

## 3. 对象模型：**只新增 1 个对象、改造 3 个**

| 对象 | 宿主 | 格式抄谁 | 谁写 | 现状 |
|---|---|---|---|---|
| **需求**（新） | `task-data/requirements.md`（节式，与 `decisions.md` 同款） | **抄对账账本 A 表的状态五档** + ADR-002 的证据四档 | agent 经 MCP；你只点头 | 无 |
| **规划**（新） | `task-data/plans/<项目id>.md` | 抄 Milestone plan + R5 三节 | 一期外部 agent 写；终局方寸自己写（门槛第 2 条） | 无 |
| **卡**（改） | 已有 `task-data/*.md` | 加 `判据:` 字段 | 建卡的 agent | 173 张 |
| **决策卡**（改） | 已有 `task-data/decisions.md` | ADR 四段（上下文/决策/考虑过的/后果）进 `备注` | 你 + agent | 32 条 |
| **机检报告**（改） | 已有 `shared/mismatch.ts` | 3 类 → **8 类** | 纯函数，零 LLM | 3 类 |

**明确不新增**（每一条都是"看起来该有、但一期不做"）：

- ✗ 里程碑独立对象 → 它是规划文件里的一张表（REV-008 一期只做 1+2）
- ✗ 验收段独立对象 → 判据是需求的属性，证据是卡的属性（第 4 段留位不施工）
- ✗ 发布段 / 运维段 / 复盘段对象 → REV-008 明写留位不施工
- ✗ 需求与卡之间的"关联对象" → 用卡上一个 `需求:` 字段，不建关联表

> **为什么"只新增 1 个"是关键**：ADR-001 的教训是每轮都想补齐七段。一期新增对象每多一个，就要多一套解析（TS + Python 两腿）、多一个视图、多一套守卫 —— 这是 175 次提交只换来"只用日志"的直接原因。

## 4. 字段级设计（可直接施工）

### 4.1 需求条（`task-data/requirements.md`，节式）

```markdown
## RQ-fangcun-001 方寸能报出"过去 N 天花了多少 token、产出几件真被用起来的"
- 日期: 2026-10-29
- 状态: 提出          # 提出 / 已拍 / 在做 / 做完 / 已否   ← 抄对账账本 A 表五档
- 项目: 方寸
- 来源: 亲口          # 亲口 / 实测 / agent推断 / 直觉     ← 复用 ADR-002 的 C 值证据四档
- 判定: num: 时间窗内 token 合计 > 0 且 产出件数 >= 0
- 判定: file: docs/产出清单.md 存在且每行含 需求id
- 挂卡: task-20261029-001, task-20261029-004
- 拍板: D-041
- 备注: 
```

**规则（全部可机检）**
- `状态` 五档之外的写法 → 拒收该条，不拒整批
- `判定:` 至少一行；空 → 机检第 4 类报「需求没判据」
- `判定:` 前缀只认四类：`file:` / `str:` / `num:` / `cmd:`；写 `human:` 合法但**不算可机检判据**
- `挂卡:` 里引用的卡 id 不存在 → 机检报引用断裂（复用现有第 2 类）
- 幂等：同 RQ id 再灌，覆盖判定与备注，**保留已存在的 `拍板:`**

### 4.2 规划（`task-data/plans/<项目id>.md`）

```markdown
# 方寸 · 当前规划（v3，2026-10-29）

## 顺序
1. M0 判据落地 —— 因为 R2 卡着 R1（没有判据，token 挂不上需求）
2. ...

## 依赖
| 项 | 依赖谁 | 依赖是否满足 | 判据 |

## 砍掉什么
| 砍掉的 | 为什么砍 | 什么时候可以捡回来 |

## 里程碑
| 阶段 | 交付物 | 判据 | 依赖 | 状态 |
|---|---|---|---|---|
| M0 | 卡上 `判据:` 字段 + mismatch 升级 | mismatch「完成但没判据」= 0 | 无 | 待开始 |
```

**规则**
- **三节缺一 = 不合格**（R5 原话「只有条目的不叫规划」）。缺了页签标红，**但不阻挡**（REV-008）
- 「砍掉什么」允许空表，但必须显式写「本期无砍」—— 空着不说 = 不合格
- 规划是**项目级**文件，每项目一份（塞一个文件里必然打架）

### 4.3 卡的判据（**关键设计**：不动已有的 137 张）

`验收:` 字段**保留原义 = 谁来验**（人）。新增 `判据:` = **凭什么验**（机器）。两者分工，不互相覆盖。

```yaml
验收: 暮雨                      # 谁验（已有，不动）
判据:                           # 凭什么验（新增）
  - cmd: node scripts/test/e2e-rice.cjs        # 退出码 0
  - str: desktop/src/shared/mismatch.ts 含 'nocriteria'
  - num: task-data/rice-pool.md 条目数 >= 0
```

- 四类前缀：`cmd:` / `str:` / `file:` / `num:`；`human:` 合法但不可机检
- **为空 → 机检第 3 类报红**（不阻挡，卡照建）
- 存量处置见第 7 节 M0：**57 张完成卡直接标「完成(未验证)」，不重写**

### 4.4 决策卡的 ADR 模板（不新增字段）

`decisions.md` 已有 `## D-xxx 标题` + `- 键: 值` + `备注:` 多行。**ADR 四段写进 `备注:`，不扩接口**（ADR-002 已定的判据：`Decision` 接口零扩展）。

```markdown
## D-041 方寸：判定权内置、生成分两段
- 日期: 2026-10-29
- 状态: 有效
- 项目: 方寸
- 出处: docs/adr/ADR-003
- 备注: 
  ADR
  - 上下文: 外包失败不可修；缺的是判定权不是判断质量
  - 决策: 判定权内置 / 生成分两段 / 编排不进本体
  - 考虑过的: 纯外包（否）· 全内置编排（否）· 只加派活按钮（否，第二个规划按钮）
  - 后果: 一期方寸仍不出规划；换取失败可修
```

带 `ADR` 标记的决策卡，**四段缺一 → 机检第 8 类报**。

## 7. 施工里程碑（每步带验收判据，先判据后生成）

### M0 · 判据落地（1–2 天）
- 卡加 `判据:`（`TASK_FIELD_SPECS` + `FM_ORDER` 同步 + 两侧解析 + 模板）
- `mismatch` 第 3 类改为读 `判据:` 字段（不再靠正文关键词）
- **存量分桶**：57 张「完成+无判据」→ 标 `完成(未验证)`，**不重写**；68 张活卡导出清单交 agent 补
- **判据**：mismatch 第 3 类 = 0；新建一张不带 `判据:` 的卡 → 红标出现（反例）

### M1 · 需求对象（2–3 天）
- `requirements.md` 节式解析（TS + Python 两腿，**逐字节对账**，抄 ADR-002 的双腿做法）
- MCP 写口 `requirement_upsert`（幂等，抄 `rice_pool_upsert`；**不开第二写口**）
- 卡加 `需求:` 字段；项目页「需求」页签
- **判据**：任一张卡能回答"挂在哪条需求上"；挂不上的计数非零且可列出；同 id 连灌两遍条数不变

### M2 · 规划对象（3 天）
- `plans/<项目id>.md` 解析 + 三节强制 + 里程碑表
- 一期：外部 agent 经 MCP 写，方寸只收单机检（ADR-003 决策 2）
- 项目页「规划」页签 + 顶部机检条
- **判据**：缺一节 → 页签标红且不显示"合格"；「砍掉什么」空着不说 → 报

## 9. 这套设计的失效条件（诚实写出来）

1. **M0 跑不出可机检的判据** → 后面全是空转。这是**唯一的真风险**，也是第一步就做它的原因。
2. **需求由你写** → R6 明写「不要求用户写」，需求必须 agent 起草你只点头；若变成你填表，M1 会死在没人填。
3. **新增对象超 2 个** → 每多一个对象多一套双腿解析 + 视图 + 守卫，会重演"175 次提交只用日志"。
4. **机检报红变成噪音** → 8 类同时报几百条 = 没人看。缓解：对不上页签**按类折叠 + 只默认展开计数最大的两类**。

## 附：本方案没做的事

- 没做权限矩阵、端型矩阵、异常状态全枚举 —— 方寸是**单人使用的本地工具**，这些是多人协作系统的产物。硬套等于给工具箱配审批流。
- 没做竞品与市场规模 —— 无数据即不写（REV-007 的竞品组件另走，与本方案无关）。
- 没定数据库与接口细节 —— 一律「待研发确认」，本方案只定**对象、字段、判据、界面位置**。
